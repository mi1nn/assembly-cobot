# 시스템 구성도 및 작업 순서 (v2 — 실제 구현 기준)

> 이 문서는 `시스템_구성도_및_작업순서.md`(초안)를 대체하는 개정판입니다.
> 초안은 FastAPI + React + 단일 프로세스 rclpy 통합을 가정한 초기 구상이었으나,
> 실제 구현은 Flask + 별도 ROS2 Bridge + HTML/JS 방향으로 진행되었습니다.
> `web_app/`(과거 `ws_backend/`에서 이름 변경)과 `src/` 코드를 기준으로 현재 상태를 기술합니다. 초안은 과거 구상 기록으로 남겨둡니다.
>
> **2026-08 갱신**: `web_app`의 프론트엔드·백엔드·DB는 완성 단계(Work Order/Robot/Dashboard CRUD, 강제정지·복구, 시스템 로그까지 전 구간 연동)에 들어갔습니다. 이번 개정은 그 완성된 흐름을 기준으로 구성도·작업 순서·이슈 목록을 갱신합니다.

## 1. 시스템 아키텍처

```
┌───────────────────────┐
│  Frontend             │  HTML / CSS / JavaScript (web_app/frontend)
│  Work Order / Robot / │
│  Dashboard / Log UI   │
└──────────┬────────────┘
           │ HTTP / REST
           ▼
┌───────────────────────┐
│  Flask Backend        │  web_app/app
│  (REST API +          │
│   SQLAlchemy ORM)     │
└──────────┬────────────┘
           │
           ├──────────────► PostgreSQL (로컬 설치)
           │
           │ HTTP / REST  (BRIDGE_BASE_URL, 기본 http://127.0.0.1:8001)
           │  /jobs, /works/<id>/stop, /robots/<id>/recover, /health, /status
           ▼
┌─────────────────────┐
│  ROS2 Bridge Node     │  src/ros2_bridge (별도 프로세스)
│  - Flask HTTP 서버     │
│    (내장, 8001 포트)   │
│  - rclpy Action Client │
│  - rclpy Service Client│  (StopOperation, RecoverRobot)
│  - rclpy Subscriber    │  (/system_event)
└──────────┬───────────┘
           │ ROS2 Action (execute_operation)
           │ ROS2 Service (stop_operation, recover_robot)
           │ ROS2 Topic  (/system_event, 역방향)
           ▼
┌──────────────────────┐
│  Robot Control Node  │  src/solar_panel_robot
│  (Controller)        │
└──────────┬───────────┘
           ▼
┌───────────────────────┐
│  Doosan M0609         │
│  + Gripper            │
│  + F/T Sensor         │
└───────────────────────┘
```

> **설계 원칙**: Backend(Flask)와 ROS2 Bridge를 별도 프로세스로 분리하고 HTTP로 통신한다. Backend는 ROS2/rclpy에 직접 의존하지 않으며, Bridge가 HTTP 요청을 ROS2 Action/Service 호출로 변환하는 역할을 전담한다.

## 2. 기술 스택

| 구분 | 기술 |
|---|---|
| Frontend | HTML / CSS / JavaScript (`web_app/frontend`) |
| Backend | Python / Flask (`web_app/app`) |
| ORM | SQLAlchemy (Flask-SQLAlchemy) |
| DB | PostgreSQL (로컬 설치, `psycopg2`) |
| Backend ↔ ROS2 Bridge | HTTP / REST (`requests`, `BRIDGE_BASE_URL`) |
| ROS2 Bridge | Python / rclpy + Flask (내장 HTTP 서버) |
| ROS2 | ROS2 Jazzy, rclpy |
| 로봇 플랫폼 | Doosan M0609, DART Platform / DART Studio |
| 개발 환경 | Ubuntu 24.04, Linux |

## 3. 코드 구조와 실제 컴포넌트

| 위치 | 역할 |
|---|---|
| `web_app/app/routes/` | Work Order CRUD·실행·강제정지(`work_orders.py`), Bridge 콜백(`executions.py`), 로봇 목록·복구(`robots.py`), 대시보드 집계(`dashboard.py`), 로그(`logs.py`), 헬스체크·페이지(`health.py`, `pages.py`, `bridge.py`) |
| `web_app/app/services/bridge_service.py` | Bridge에 HTTP로 작업 제출(`/jobs`)·강제정지(`/works/<id>/stop`)·복구(`/robots/<id>/recover`)·헬스체크(`/health`) 요청, Work Command 조립 |
| `web_app/app/services/execution_service.py` | Work/Operation Execution 상태 전이(진행·완료·실패·취소·강제정지·로봇 복구) 전담 |
| `web_app/database` | PostgreSQL 스키마(`schema.sql`), seed, 계정/권한 스크립트 |
| `web_app/frontend` | 정적 HTML/JS 대시보드 — Work Order 생성/조회/실행/강제정지, 로봇 상태/복구, 시스템 로그 조회 UI 포함 |
| `src/ros2_bridge/ros2_bridge/bridge_node.py` | ROS2 Bridge 노드. Flask HTTP 서버(포트 8001)와 rclpy `ActionClient`/`ServiceClient`/`Subscription`을 한 프로세스에서 실행. 작업 큐 순차 전송, 강제정지·복구 요청을 Service로 변환, `/system_event`를 구독해 Backend `/api/v1/logs`로 전달 |
| `src/solar_panel_interface` | 커스텀 인터페이스 정의: `ExecuteOperation.action`, `Parameter.msg`, `SystemEvent.msg`, `StopOperation.srv`, `RecoverRobot.srv` |
| `src/solar_panel_robot/solar_panel_robot/controller_node.py` | 실제 로봇 Controller. Action 이름을 절대 경로 `/execute_operation`으로 등록해 Bridge와 일치시킴. `resolve_operation_code()`로 DB `operation.code`(`postA`~`postF` 등)를 검증하고 실행 |
| `src/solar_panel_robot/solar_panel_robot/coordinate_manager.py` | (폐기 예정) Frame 좌표계(UCS) 생성 유틸(P1/P2/P3 기반). 2026-08 설계 변경으로 Frame 좌표계 측정 자체가 폐기되어 `solar_motion.py` 공정 흐름에 통합할 계획 없음 |
| `src/solar_panel_robot/solar_panel_robot/ros_bridge_node.py` | Controller를 직접 호출하는 또 다른 Action Client 노드. `setup.py` entry_points에 등록되어 있지 않아 실행되지 않는 미사용 코드 |
| `src/solar_panel_robot/solar_panel_robot/action_server.py` | 테스트용 Mock Action 서버. `ExecuteOperation` Action에 더해 `StopOperation`/`RecoverRobot` Service까지 모두 구현되어 있어, 현재 Backend의 강제정지/복구 기능은 **이 Mock을 상대로만 end-to-end 검증됨** |

## 4. 알려진 미해결 이슈 (구현 정합성)

- **강제정지/복구 서비스가 실제 Controller에는 없음**: `bridge_node.py`는 Backend의 `/works/<id>/stop`, `/robots/<id>/recover` 요청을 ROS2 Service(`StopOperation`, `RecoverRobot`) 호출로 변환하지만, 이 서비스 서버는 `action_server.py`(Mock)에만 구현되어 있고 실제 `controller_node.py`에는 없다. 즉 Backend → Bridge → 실제 로봇까지의 강제정지/복구 경로는 아직 완결되지 않았다.
- **`coordinate_manager.py` 폐기 예정**: Frame 좌표계(P1/P2/P3) 생성 유틸은 구현되어 있으나, 2026-08 설계 변경으로 Frame 좌표계 측정 자체가 더 이상 사용하지 않는 기술로 확정되어 `solar_motion.py` 공정 시나리오에 통합할 계획이 없다. 상세는 CLAUDE.md·`docs/10_최종_시스템_시나리오.md` 참조.
- **브릿지 역할의 중복 구현**: `ros2_bridge.bridge_node.Ros2BridgeNode`(HTTP 서버 내장, Backend와 연결, canonical)와 `solar_panel_robot.ros_bridge_node.ROSBridgeNode`(HTTP 없음, entry_point 미등록으로 실행 자체가 안 됨)가 별도로 존재한다. 후자는 삭제 후보로 정리 필요.

이번 개정에서 코드는 수정하지 않았으며, 위 항목은 "web_app은 완성 단계이지만 로봇 실물 연동까지 포함한 전체 시나리오는 아직 미완결"이라는 현재 상태를 그대로 기록한 것이다.

## 5. 데이터베이스 테이블 (`web_app/database/schema.sql` 기준, 9개 테이블)

| 테이블 | 역할 |
|---|---|
| `installation` | 설치 대상 기준정보 (프로젝트/사이트/타겟) |
| `operation` | Installation별 작업 단계 정의 (순서, 파라미터 JSONB) |
| `robot` | 로봇 기준정보 |
| `sensor` | 로봇에 연결된 센서(F/T 등) 기준정보 |
| `work_order` | 작업 지시 |
| `work_execution` | Work Order의 실행 인스턴스 (로봇 배정) |
| `operation_execution` | Work Execution 내 Operation별 실행 기록 (retry_count 포함) |
| `log` | 이벤트/에러/시스템/로봇 로그 (EVENT, ERROR, SYSTEM, ROBOT) |
| `sensor_data` | Operation Execution 단위로 기록되는 센서 원시 데이터 (JSONB) |

> `sensor_data`는 `web_app/app/models/sensor_data.py`로 매핑되어 `GET /api/v1/sensor-data`로 조회 가능하다. `sensor`는 아직 모델 매핑 없음.

## 6. 작업 순서 (설치 공정)

1. **포스트(Post) 설치** — 픽앤플레이스로 지그에 삽입
2. **락핀(Lock Pin) 삽입** — 기둥-주춧돌 체결, 2단계 힘 제어 삽입 (F/T 센서로 삽입 완료 판정)
3. **프레임(Frame) 조립** — 포스트 위 프레임 결합 후 스냅핏 체결
4. **솔라 패널 목업 설치** — 스냅핏 체결로 Frame에 설치, F/T 센서로 접촉 확인

> **2026-08 설계 변경**: Frame 좌표계 측정(User Frame 기준 위치 보정) 단계는 더 이상 사용하지 않는 기술로 확정되어 제거했다.

> **알려진 한계**: 패널 설치 완료 후 그리퍼 릴리즈 시점의 패널 고정 여부는 F/T 센서만으로 확인이 불가능하며, 이는 최종 발표에서 명시적으로 고지할 예정이다.

```
Step 1. 개발 환경 구성 (Ubuntu 24.04, ROS2 Jazzy, Python, Flask)              — 완료
   ↓
Step 2. PostgreSQL 구축 (로컬 설치)                                            — 완료
   ↓
Step 3. Flask 기본 서버 구축                                                  — 완료
   ↓
Step 4. Flask ↔ PostgreSQL 연결 (SQLAlchemy ORM)                             — 완료
   ↓
Step 5. Work Order / Robot / Dashboard / Log REST API 구현                   — 완료
   ↓
Step 6. HTML/JS Dashboard 연결 (조회/실행/강제정지/로봇 복구/로그)            — 완료
   ↓
Step 7. ROS2 Bridge Node 구축 (HTTP 서버 + Action/Service Client)             — 완료
   ↓
Step 8. Flask ↔ ROS2 Bridge 통신 (작업 제출/강제정지/복구/헬스체크)          — 완료
   ↓
Step 9. ROS2 Action/Service로 실제 Robot Controller 연결                     — 진행 중
        (Action 이름 정합성은 해소됨; §4의 StopOperation/RecoverRobot
         서비스 미구현으로 강제정지·복구는 Mock에서만 검증된 상태)
   ↓
Step 10. 실행 상태 / 결과 DB 기록 (Feedback·Result 콜백, SystemEvent 로그 반영)  — 완료
   ↓
Step 11. Dashboard 상태 조회 (Work Order 진행률, 로봇 상태, 시스템 로그)         — 완료
   ↓
Step 12. 전체 시나리오 통합 테스트 (실물 로봇)
```
