## 01. 프로젝트 개요

안녕하십니까, 저희 팀은 두산로보틱스 M0609 협동로봇을 이용해 **지상형 태양광 패널 구조물의 조립 공정을 자동화**하는 프로젝트를 진행했습니다.

**기획 배경**
**1. 현장 환경의 근본적 한계 — 비전 시스템의 취약성**

- 옥외 설치 현장은 조명 조건이 시간대·날씨에 따라 계속 변하고, 먼지·분진 노출이 상시적임
- 특히 태양광 패널은 표면 반사율이 높아, 카메라 기반 인식 시 오검출·오작동 위험이 구조적으로 존재
- 즉, 비전 시스템은 "고급 기능"이 아니라 이 현장에서는 오히려 **신뢰성을 떨어뜨리는 리스크 요인**이 될 수 있음

**2. 건축·설치 공정의 특성 — 이미 정해진 답이 있는 작업**

- 태양광 패널 설치는 사전 설계도(시공도면)에 따라 포스트·프레임·패널의 설치 위치와 순서가 이미 확정되어 있는 작업
- 즉, 로봇이 "무엇을, 어디에 둘지 스스로 판단"할 필요가 없는 **정형화된 반복 조립 공정**
- 이런 공정 특성상, 상황을 해석하고 판단하는 비전/음성/LLM보다 정해진 시퀀스를 정확하고 일관되게 수행하는 능력이 더 중요

**3. 결론 — 센서 없는 게 아니라, 이 공정에 맞는 센서를 선택한 것**

- 화려한 인식 기술 대신, 로봇 내장 F/T(힘/토크) 센서로 삽입 저항·스냅핏·접촉력을 직접 측정하여 작업 성공 여부를 검증
- "본다"가 아니라 "만져서 확인한다" — 환경 변수에 흔들리지 않는 검증 방식
- 정형화된 설계도 기반 공정 + 접촉 기반 검증 = 이 프로젝트에 최적화된 기술 선택

**핵심 공정 순서**
> 기둥 설치 → 프레임 설치 → 잠금핀 체결(2단계 삽입) → 패널 설치

**차별화 포인트 — 이 프로젝트의 핵심 기술**
1. **F/T 센서 기반 힘 제어 삽입**: 잠금핀을 정해진 깊이까지 1차 삽입한 뒤, 그리퍼를 다시 잡고(재파지) 축 방향으로 압력을 가해 최종 삽입합니다. 삽입 중 저항이 과도하면 힘을 감지해 즉시 후퇴합니다.

**제외 범위**: 비전 기반 형상 인식, 임의 위치 자동 탐색, 자석 체결, 볼트·너트 자동 체결은 이번 프로젝트 범위에서 제외했습니다.

**활용 장비 및 개발환경**
- 로봇: 두산로보틱스 M0609 (그리퍼 + 내장 F/T 센서)
- OS/미들웨어: Ubuntu 24.04, ROS2 Jazzy
- 로봇 프로그래밍: DART Platform / DART Studio, DRL(Python 기반)
- DB: PostgreSQL (Work Order / Recipe 기반 스키마)

**기대 효과**: 반복 조립 작업의 자동화, 현장 사고율 감소, 그리고 작업 이력·측정 결과를 데이터로 남겨 후속 재고 관리·품질 관리에 활용할 수 있다는 점에서 실무 활용 가능성을 봤습니다.

## 03. 프로젝트 수행 절차 및 방법

**사전 기획 단계**
- 비즈니스 요구서(BR) → 시스템 요구서(SYS-FR) → 기능 요구서(FR) → 테스트 케이스(TC)로 이어지는 **요구사항 추적 체계**를 먼저 세웠습니다. BR 6개, SYS-FR 24개, FR 25개, TC 24개로 정리해서, 기능을 구현할 때도 "이게 어떤 요구사항에 대응하는지"를 놓치지 않도록 했습니다.
- 시스템을 4개 Actor(현장 관리자, 협동로봇 작업 관리 노드, DB, 협동로봇 제어 시스템)로 나누고, 이 Actor 사이의 인터페이스(ROS2 Action/Service/Topic, DB API)를 먼저 문서로 확정한 뒤 구현에 들어갔습니다.

**수행 단계 (구현 순서)**
1. `solar_panel_interface` — Bridge ↔ Controller가 주고받을 ROS2 Action/메시지 규격 정의 (계약 우선 설계)
2. `solar_panel_robot` — 저수준 모션(`robot_motion.py`), F/T 힘 제어(`force_control.py`), 공정 시나리오(`solar_motion.py`), Action Server(`controller_node.py`) 순으로 구현
3. `ros2_bridge` — Backend의 HTTP 요청을 큐에 쌓아 ROS2 Action Goal로 순서대로 전달하고, 결과를 다시 Backend로 콜백하는 중계 노드 구현
4. `web_app` — Work Order/Recipe/실행 이력을 관리하는 Flask 백엔드 + PostgreSQL 스키마(9개 테이블) + 대시보드 구현

## 04. 프로젝트 수행 경과

**시스템 아키텍처**

```
Dashboard(HTML/JS) → Flask Backend(web_app) → PostgreSQL
                            │ HTTP
                            ▼
                    ROS2 Bridge (src/ros2_bridge)
                            │ ROS2 Action
                            ▼
                  Controller (src/solar_panel_robot)
                            │
                            ▼
                    Doosan M0609 + Gripper + F/T Sensor
```

**레이어별 구현 결과**

- **`solar_panel_interface`**: Bridge-Controller 간 통신 규격만 정의하는 패키지입니다. `ExecuteOperation.action`(Goal/Result/Feedback), `Parameter.msg`, `SystemEvent.msg`를 정의했습니다.
- **`solar_panel_robot`**: 실제 로봇을 움직이는 핵심 계층입니다.
  - `robot_motion.py`: movej/movel 등 두산 SDK 함수를 감싼 범용 모션 라이브러리 — pick/place, 원점 복귀, 힘 감지 이동, 그리퍼 on/off
  - `force_control.py`: F/T 센서 기반 Compliance(순응 제어) on/off, 목표 힘 설정, 힘 조건 체크 — 잠금핀 삽입 로직의 핵심
  - `solar_motion.py`: 프레임 Pick→배치→설치, 핀 Pick→1차/최종 삽입 등 공정별 상위 시나리오
  - `controller_node.py`: Bridge로부터 Action Goal을 받아 어떤 Operation인지 판단하고 `SolarMotion`에 실행을 위임하는 Action Server
- **`ros2_bridge`**: Flask HTTP 서버(포트 8001)와 ROS2 ActionClient를 한 프로세스에서 같이 운용합니다. Backend의 `/jobs` 요청을 큐에 쌓아 순서대로 Controller에 전달하고, Feedback/Result를 Backend 콜백(`/action-feedback`, `/action-result`)으로 다시 전달합니다.
- **`web_app`**: Work Order/Recipe/Operation/실행 이력을 관리하는 Flask 백엔드 + PostgreSQL 9개 테이블 스키마 + 대시보드(HTML/JS)로, 작업 지시부터 진행 상태 조회까지 지원합니다.

**결과 제시 (스크린샷/데모 삽입 위치)**
- [ ] 대시보드에서 Work Order 생성 → 실행 화면 캡처
- [ ] 잠금핀 삽입 시 F/T 센서 힘 그래프(저항 감지 → 후퇴 또는 최종 삽입) 캡처
- [ ] 패널 설치 완료 후 전체 구조물 사진/영상

**진행 중 확인된 이슈** (정직하게 짚고 갈 부분)
- `controller_node.py`의 `.action` 인터페이스(Feedback 스키마)와 실행 가능한 Operation 이름 체계가 DB/Bridge 쪽과 아직 완전히 맞지 않아, 실제 로봇 연동 테스트는 이 부분을 먼저 맞춘 뒤 진행했습니다. [실제 해결 여부에 맞게 수정]
- `SystemEvent.msg`(Controller → Bridge 오류/이벤트 알림)는 정의만 되어 있고 publish/subscribe 코드는 아직 없어 로그 조회 API(`app/routes/logs.py`)와 연결되지 않은 상태였습니다. [해결 여부에 맞게 수정]

## 05. 자체 평가 의견

**완성도 평가 (10점 만점 기준 예시 문구 — 실제 점수/근거로 교체)**
> 사전 기획 단계에서 세운 목표(기둥→프레임→잠금핀 체결→패널 설치)를 [O/10] 수준까지 구현했습니다. 특히 F/T 센서 기반 힘 제어 삽입이라는 핵심 차별화 포인트는 [완성/부분 구현] 되었습니다.

**잘한 점**
- BR → SYS-FR → FR → TC로 이어지는 요구사항 추적 체계를 먼저 세우고 개발해서, "왜 이 로직이 필요한지"를 팀 전체가 같은 기준으로 판단할 수 있었습니다.
- 통신 인터페이스(`solar_panel_interface`)를 계약처럼 먼저 정의하고 각 레이어(로봇 제어 / Bridge / Backend)를 병렬로 개발할 수 있었던 점.
- 실제 산업 조립 공정을 모사한다는 목표에 맞게, 단순 좌표 이동이 아니라 힘 제어라는 실무적인 기술을 구현에 반영한 점.

**아쉬운 점 / 추후 개선점**
- 인터페이스 스키마 불일치(Feedback 필드, Operation 이름 체계)처럼 레이어 간 계약을 문서로만 맞추고 초기 구현 검증이 늦어져 통합 시점에 발견된 이슈가 있었습니다. → 다음에는 계약 정의 직후 스텁(mock) 기반 통합 테스트를 더 일찍 붙이면 좋겠습니다.
- `SystemEvent`처럼 정의만 하고 실제 연결은 미룬 부분이 있어, 오류 로그가 DB까지 온전히 흐르지 않는 경우가 있었습니다.
- F/T 센서 임계값처럼 실측 후 확정해야 하는 값들을 처음부터 Recipe/Parameter로 분리해 관리한 덕분에 튜닝은 수월했지만, 실제 튜닝에 걸린 시간은 [예상보다 길었음/짧았음] — 하드웨어 캘리브레이션 일정을 더 넉넉히 잡을 필요가 있습니다.

**경험/성과**
- ROS2 Action 기반 다단계 작업 파이프라인(작업 관리 노드 ↔ Controller ↔ 로봇), DB 연동 Work Order/Recipe 관리 구조를 처음부터 끝까지 설계·구현해본 경험.
- [팀/개인 차원에서 느낀 점, 진로 연관성 등 자유 기술]
