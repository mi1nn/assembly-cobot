# 01. 프로젝트 개요

## 1-1. 선정 배경 (PDF p.3) — 약 50초

"이 프로젝트는 **옥외 태양광 설치 현장의 특성을 반영한 의도적 설계 선택**에서 출발했습니다.

- **비전 인식에 불리한 환경입니다.** 옥외는 조명·먼지 변화가 크고, 패널 표면은 반사율이 높습니다.
  카메라 기반 인식은 여기서 신뢰성을 떨어뜨리는 리스크가 됩니다.
- **작업자 위험이 큽니다.** 태양광 설치는 지붕 추락과 전기 감전 사고가 잦습니다.
  실제로 최근 5년간 태양광 공사 사고 사망자 25명 중 다수가 떨어짐 사고였고,
  2024년 한 해에만 떨어짐 사망자 8명이 발생했습니다. (고용노동부·한국산업안전보건공단 자료)
- 그래서 저희는 **정형화된 반복 조립 공정에 F/T 센서 기반 접촉 검증을 적용**하는,
  차별화된 자동화 사례를 목표로 잡았습니다."

## 1-2. 프로젝트 내용 · 구조 (PDF p.4) — 약 40초

"**프로젝트 내용**은 이렇습니다. 기둥 → 프레임 → 스냅핏 체결 → 패널 설치, 이 **4단계 조립을
F/T 센서로 검증하며 자동 수행**하고, **MES 연동 대시보드로 공정을 관리**합니다.

**프로젝트 구조**는 —
- 목적: 비전 없는 F/T 기반 조립 자동화 구현
- 기간: 2주, 사전 기획부터 통합 테스트까지
- 구성: **Dashboard – Backend – Bridge – Robot 4계층**
- 의존성: ROS2 Jazzy, Python 3, Flask·Flask-SQLAlchemy·SQLAlchemy·python-dotenv·psycopg2·requests, PostgreSQL 16"

## 1-3. 활용 방안 및 기대 효과 (PDF p.5) — 약 1분

"이 기술은 **반사율 높은 옥외 부품 조립에 그대로 적용 가능**하고, 협동로봇 자동화 사례로 활용할 수 있습니다.
시장 근거를 두 가지로 말씀드리겠습니다.

**① 시장은 빠르게 성장하고 있습니다.** (건설 로봇 시장, ResearchNester)
- 기준 연도 2025년 시장 규모 **14억 6천만 달러**, 2035년 **60억 6천만 달러**로 예측됩니다.
- 예측 기간 2026~2035년 **연평균 성장률(CAGR) 15.3%** — 10년간 4배 이상 커지는 시장입니다.
- 지역별로는 북미, 아시아태평양, 유럽, 라틴아메리카, 중동·아프리카 전역에 걸쳐 있습니다.

**② 로봇 도입의 절감 효과가 이미 수치로 검증되고 있습니다.**
- **AES Maximo**: 기존 대비 **설치 비용 50% 절감**, **설치 시간 50% 단축**.
  2025년 100MW 설치 목표, 3년 내 최대 5GW 파이프라인(美 백로그 약 4GW).
- **독일 PV Kraftwerker · Gehrlicher 로봇** (IEEE Spectrum 보도):
  14MW 발전소 기준 설치 비용 **200만 달러 → 90만 달러(약 55% 절감)**,
  설치 속도 **최대 8배**, 투입 인력 **35명 → 3명**. 로봇 도입 비용은 100만 달러 미만이고
  **1년 이내에 투자비 회수**가 가능합니다.
- 요약하면 — 로봇으로 14MW 태양광 발전소를 지으면, 비용은 절반 이하로,
  인력은 1/10로, 공기는 최대 8배 빠르게 줄일 수 있습니다.

저희 프로젝트는 이 흐름에서 '비전에 의존하지 않는 접촉 기반 조립'이라는 접근을 검증한 사례입니다."

> 출처 표기: ResearchNester(시장 규모·성장률), AES Maximo, IEEE Spectrum. `report.md`에 상세 있음.

## 1-4. 핵심 공정 순서 (PDF p.6) — 약 40초

"핵심 공정은 **4단계 순차 조립**입니다.

1. **기둥 설치** — 픽앤플레이스로 주춧돌 지그에 삽입
2. **프레임 설치** — 기둥 위 프레임 결합
3. **스냅핏 체결** — F/T 센서로 체결력 검증
4. **패널 설치** — Frame에 패널 설치 후 스냅핏 체결

한 가지 중요한 범위 조정 — **기둥과 주춧돌의 고정핀 체결은 로봇·작업자 협동 작업으로,
사람이 수행하는 것으로 대체**했습니다. 협동로봇의 본래 취지에 맞춘 역할 분담입니다.

**제외 범위**는 비전 형상 인식, 임의 위치 자동 탐색, 자석 체결, 볼트·너트 자동 체결입니다.
**장비·환경**은 두산 M0609(그리퍼 + 내장 F/T), Ubuntu 24.04, ROS2 Jazzy, DART Platform/DRL, PostgreSQL입니다."

## 1-5. 이 프로젝트의 핵심 기술 — F/T 센서 기반 힘 제어 삽입 (PDF p.7) — 약 1분

"이 프로젝트의 핵심 기술은 **F/T 센서 기반 힘 제어 삽입**입니다.
정해진 깊이까지 1차 삽입한 뒤 재파지해서 축 방향으로 최종 삽입하고,
**과도한 저항이 감지되면 즉시 후퇴**해 안전을 확보합니다. 두 가지 프로세스로 씁니다.

**스냅핏 체결 프로세스**
1. **1차 삽입** — 정해진 깊이까지만
2. **재파지** — 그리퍼로 다시 파지
3. **최종 삽입** — 축 방향 가압, 저항 감지 시 후퇴

**기둥 삽입 프로세스**
1. **기둥 삽입** — 정해진 깊이까지
2. **위치 추적** — 체결 위치가 안 맞으면 미세한 x·y 좌표 조정
3. **최종 삽입** — 축 방향 가압, 저항 감지 시 후퇴

공통 원칙은 **'저항이 임계값을 초과하면 후퇴하거나 위치를 조정한다'** — 환경 변수에 흔들리지 않는
접촉 기반 검증입니다.

**코드로는** `force_control.py`의 `ForceController`가 두산 SDK의 `task_compliance_ctrl`(순응 제어)과
`set_desired_force`(목표 힘)를 감쌉니다. 실제 삽입은 `robot_motion.py`의
`place(axis, direction, force, threshold)` — 축으로 힘을 가하다 **반력이 threshold를 넘으면 정지**합니다.
그 직전 `_search_post_alignment()`가 접촉점 주변을 force probe로 훑어 삽입 가능한 정렬점을 찾습니다.

**설계 결정 하나** — F/T 임계값은 실측 후에나 확정되는 값이라 코드에 하드코딩하지 않고
전부 DB의 Recipe/Parameter(`operation.parameter`, JSONB)로 분리했습니다. 현장에서 값만 바꿔 튜닝합니다."

# 03. 수행 절차 및 방법

## 3-1. 사전 기획 — 요구사항 추적 체계 (PDF p.9) — 약 50초

"구현에 들어가기 전에 **BR → SYS-FR → FR → TC로 이어지는 추적 체계**를 먼저 세웠습니다.

- **BR** 비즈니스 요구서 6개
- **SYS-FR** 시스템 요구서 24개
- **FR** 기능 요구서 24개
- **TC** 테스트 케이스 15개

기능을 구현할 때마다 '이게 어떤 요구사항에 대응하는지'를 팀 전체가 같은 기준으로 판단할 수 있었습니다.

그리고 시스템을 **4개 Actor**로 나눴습니다 — 현장 관리자, 협동로봇 작업 관리 노드, DB, 협동로봇 제어 시스템.
Actor 간 인터페이스(ROS2 Action/Service/Topic, DB API)를 **먼저 문서로 확정한 뒤** 구현에 착수했습니다."

## 3-2. 구현 순서 — 계약 우선 설계 (PDF p.10) — 약 40초

"구현은 **통신 규격을 먼저 정의하고, 로봇 제어 → 중계 → 백엔드 순서**로 진행했습니다.

1. **`solar_panel_interface`** — Action/메시지/서비스 규격 정의. 계약 우선 설계의 출발점.
2. **`solar_panel_robot`** — 모션 → 힘 제어 → 공정 시나리오 → Action Server 순.
3. **`ros2_bridge`** — HTTP 큐잉 → Action Goal 순차 전달 → 결과 콜백.
4. **`web_app`** — Work Order/History 관리 + PostgreSQL 9테이블 + 대시보드.

계약을 먼저 고정했기 때문에 로봇 제어팀과 백엔드팀이 서로를 기다리지 않고 동시에 개발할 수 있었습니다."

# 04. 수행 경과

## 4-1. 시스템 아키텍처 (PDF p.12 · p.26) — 약 1분 30초

"시스템은 **Dashboard부터 로봇 하드웨어까지 4계층 파이프라인**입니다.

```
현장 관리자
   │
Dashboard (HTML/JS)                     Work Order 조회·실행
   │ HTTP/REST
Flask Backend  (web_app, :5000)  ──►  PostgreSQL (9개 테이블)
   │ HTTP/REST  (BRIDGE_BASE_URL, 기본 :8001)
ROS2 Bridge  (src/ros2_bridge, 별도 프로세스)   HTTP ↔ ROS2 Action 변환 · Feedback/Result 콜백
   │ ROS2 Action / Service / Topic
Robot Control Node = Controller  (src/solar_panel_robot)   Operation 판단 및 실행 위임
   │
Doosan M0609 + Gripper + F/T Sensor     실제 조립 동작 수행
```

**설계 원칙 두 가지를 강조하겠습니다.**

첫째, **Backend는 ROS2에 직접 의존하지 않습니다.** Flask 백엔드는 rclpy를 import하지 않고
HTTP로만 Bridge와 통신합니다. Bridge가 HTTP 요청을 ROS2 Action/Service 호출로 번역합니다.
덕분에 백엔드팀과 로봇 제어팀이 완전히 분리되어 병렬 개발이 가능했습니다.

둘째, **로봇 제어 레이어는 DB에 직접 쓰지 않습니다.** 로봇의 상태·측정·이벤트는 전부 Bridge를 거쳐
백엔드 콜백 세 개로만 들어옵니다 — `action-feedback`, `action-result`, `logs`.
유입 경로가 좁을수록 추적과 디버깅이 쉽습니다."

## 4-2. 레이어별 구현 결과 (PDF p.13) — 약 50초

"레이어별로 무엇을 만들었는지 짧게 정리하면 —

- **`solar_panel_interface`** — `ExecuteOperation.action`, `Parameter.msg`, `SystemEvent.msg`,
  `RecoverRobot.srv`, `StopOperation.srv`. 통신 규격 정의.
- **`solar_panel_robot`** — `robot_motion.py`(저수준 모션), `force_control.py`(F/T 힘 제어),
  `solar_motion.py`(공정 시나리오), `controller_node.py`(Action Server).
- **`ros2_bridge`** — Flask(:8001) + ActionClient 단일 프로세스, Operation 큐잉·순차 전송, Feedback/Result 콜백.
- **`web_app`** — Work Order/Recipe/실행 이력 관리 + PostgreSQL 9테이블 + 대시보드(:5000)."

## 4-3. 작업 지시 1건의 여정 — 공정 시퀀스 (보충) — 약 1분 30초

"현장 관리자가 대시보드에서 READY 상태 Work Order를 '실행'하면 이렇게 흐릅니다.

1. **Backend — 실행 요청 수신** (`work_orders.py → execute_work_order`).
   Work Order가 READY인지, 로봇이 IDLE인지 확인. Operation 목록을 **sequence 순서대로** 조회.
   `WorkExecution` 1건 + Operation 수만큼 `OperationExecution`을 PENDING으로 생성 →
   `build_work_command()`로 조립 → Bridge에 `POST /jobs`. Work Order·실행·로봇을 RUNNING으로.
2. **Bridge — 큐 적재** (`bridge_node.py → enqueue_work`).
   **Operation 하나마다 job 하나**를 `job_queue`에 한꺼번에 적재.
   *Operation 실행 순서를 보장하는 건 Backend가 아니라 이 큐입니다.*
3. **Bridge — 순차 디스패치** (`process_job_queue`, 100ms 타이머).
   진행 중 Goal이 없을 때만 1건 꺼내 `ExecuteOperation.Goal`로 `send_goal_async`.
   정지된 작업의 잔여 Operation은 건너뜀.
4. **Controller — 수락 판정** (`goal_callback`).
   준비 상태, 로봇 정지 여부, ID 유효성, operation_code 지원 여부, 다른 Operation 진행 여부를 순서대로 검사.
5. **Controller — 실행** (`execute_callback → execute_operation → SolarMotion`).
   `OPERATION_STARTED` 이벤트를 `/system_event`로 발행, RUNNING feedback 후 operation_code로 분기.
   주 경로는 `install_post_cycle()` — Post Pick → Place(힘 삽입) → Stop → Release → Retreat → Home.
6. **Bridge → Backend 콜백**. feedback → `POST /executions/action-feedback` → Operation RUNNING.
   result 성공 → `POST /executions/action-result` → Operation COMPLETED, 다음 단계 **판정만**.
   다음 Operation은 이미 Bridge 큐에 있으니 재전송 없음. 남은 게 없으면 Work Order·로봇을 마감.

한 문장으로 — **Backend는 상태를 기록하고, Bridge는 순서를 지키고, Controller는 로봇을 움직입니다.**"

> 슬라이드에 시퀀스 다이어그램이 없으면 이 장면은 4-1 뒤에 붙여 말로만 진행하고, 있으면 해당 슬라이드에서.

## 4-6. 소프트웨어 상세 (PDF p.21 ~ p.25) — 약 1분 30초

"소프트웨어를 패키지별로 보겠습니다.

**`ros2_bridge` — Backend ↔ ROS2 중계** (`bridge_node.py`)
한 프로세스에 둘이 같이 떠 있습니다. ① Flask HTTP 서버(:8001) — `/health`, `/status`, `/jobs`(Operation 제출),
`/works/<id>/stop`(강제 정지), `/robots/<id>/recover`(복구). ② rclpy ActionClient — 받은 Operation을 큐에 쌓아
순서대로 Controller에 Goal 전송, Feedback/Result를 Backend `action-feedback`/`action-result`로 콜백,
Controller가 publish하는 `/system_event`를 subscribe해 Backend `/api/v1/logs`로 전달.
한 Operation이 실패하면 같은 작업의 나머지 대기 Operation은 자동으로 건너뜁니다.

**`solar_panel_robot` — 로봇 제어**
- `controller_node.py` — Action Server. Bridge Goal을 받아 `resolve_operation_code()`로 DB `operation.code`
  (postA~postF 등)를 검증하고, `SolarMotion`에 실제 동작을 위임. `/system_event`로 초기화·진행·오류·복구 이벤트 publish.
- `action_server.py` — Mock Action Server. 실제 로봇 없이 통신 흐름만 검증. 강제정지·복구 흐름도 모킹.
- `robot_controller.py` — 로봇 초기화 전용(Manual/Auto 모드, Tool/TCP 설정, 서비스 호출 재시도).
- `robot_motion.py` — 저수준 모션 라이브러리(pick/place, 원점 복귀, 힘 감지 이동, 그리퍼 on/off).
- `solar_motion.py` — 공정별 상위 시나리오. `robot_motion.py`/`force_control.py`를 조합.
- `force_control.py` — F/T 센서 기반 힘 제어(Compliance on/off, 목표 힘 설정, 힘 조건 체크).
- `coordinate_manager.py` — (폐기 예정) Frame 좌표계 생성 유틸. 2026-08 설계 변경으로 Frame 좌표계 측정 자체를
  더 이상 쓰지 않기로 확정, 공정 흐름 연동 계획 없음.
- `ros_bridge_node.py` — `setup.py`에 미등록으로 실행조차 안 되는 미사용 코드, 정리 대상.

**`solar_panel_interface` — 인터페이스 정의**
`ExecuteOperation.action`(Goal: work_order_id/operation_code 등, Feedback: STATUS_PENDING~CANCELLED, Result: success/error_code),
`Parameter.msg`(key/value), `SystemEvent.msg`(severity·code·phase·status·detail), `StopOperation.srv`, `RecoverRobot.srv`.

**`web_app` — Flask Backend**
`app/routes/`가 Work Order CRUD·실행·강제정지, Bridge 콜백, 로봇 복구, 대시보드 집계, 로그를 담당.
`app/services/`가 상태 전이(`execution_service.mark_*`)와 Bridge 통신(`bridge_service`)을 전담.
`database/schema.sql`이 9개 테이블.

**DB — PostgreSQL 9테이블**
기준정보(`installation`, `operation`, `robot`, `sensor`)와 실행 데이터(`work_execution`, `operation_execution`,
`log`, `sensor_data`). **DB에서 로봇으로 나가는 유일한 데이터 원천은 `operation.parameter`/`components`(JSONB)** —
`build_work_command()`가 그대로 ROS2 Goal에 실어 보냅니다. 상태(`status`)는 4개 테이블에 동기적으로 전이합니다."

## 4-7. 진행 중 이슈 / 한계 — 약 40초

"정직하게 짚고 갈 부분입니다.

- **강제정지·복구의 실물 검증은 아직 Mock 기준.** `StopOperation`/`RecoverRobot` 서비스가 실제
  `controller_node.py`에도 있지만, Backend→Bridge→실물까지의 end-to-end 검증은 Mock으로만 마쳤습니다.
- **F/T 실측값 DB 적재 미구현.** `sensor_data` 테이블과 조회 API는 있으나, 로봇 측정값을 넣는 콜백이 아직 없어
  힘 그래프는 seed 데이터 기준입니다.
- **패널 릴리즈 시점 고정 확인의 한계.** 그리퍼를 놓는 순간 패널이 확실히 고정됐는지는 F/T만으로 확인 불가.
- **2026-08 설계 변경** — Frame 좌표계 측정(P1/P2/P3) 단계는 폐기. 관련 코드(`coordinate_manager.py`)는 남아 있으나
  공정 흐름 연동 계획 없음.

'web_app은 완성 단계지만, 실물 로봇까지 포함한 전체 시나리오는 아직 미완결'이라는 현재 상태입니다."

## 부록. 예상 Q&A 대비 메모 (슬라이드 없음)

| 질문 | 답변 요지 |
|---|---|
| 왜 비전이 아니라 힘 센서인가? | 옥외는 조명·먼지·반사율 때문에 비전이 불리. 공정은 도면으로 확정된 정형 반복 작업이라 '판단'이 아니라 '검증'이 핵심. |
| 잠금핀 체결은 로봇이 하나? | 기둥–주춧돌 고정핀은 협동 작업으로 사람이 수행. 로봇은 스냅핏 체결·기둥 삽입에 힘 제어 적용. |
| Operation 순서는 누가 보장하나? | Bridge `job_queue`. Backend는 `receive_action_result`에서 다음 단계 판정만, 재전송 안 함. |
| 힘 임계값은 어디에 있나? | `operation.parameter`(JSONB) → `build_work_command()` → ROS2 Goal. 코드에 하드코딩 없음. |
| 로봇이 DB에 직접 쓰나? | 아니오. Bridge 콜백 3개(`action-feedback`/`action-result`/`logs`)로만. |
| Mock과 실제 Controller 차이는? | Action 이름 동일. Mock은 0→100% 가짜 진행 + 플래그만; 실제는 `SolarMotion`으로 M0609 구동. |
| 실물 로봇 연동은 어디까지? | 정상 실행 경로는 연동 검증. 강제정지·복구는 Mock 기준. F/T 값 DB 적재는 미구현. |
| 시장이 실제로 크나? | 건설 로봇 시장 2025년 14.6억 달러 → 2035년 60.6억 달러, CAGR 15.3%(ResearchNester). |
| 로봇 도입 효과는? | 14MW 발전소 기준 비용 200만→90만 달러(약 55%↓), 인력 35→3명, 속도 최대 8배, 1년 내 회수(IEEE Spectrum). |
| 왜 Flask + 별도 Bridge인가? | Backend가 rclpy에 묶이지 않게. 초안(FastAPI+React+단일 rclpy)에서 변경한 결정. |
