## 1. 기동(startup) 순서

### 1-1. Flask Backend — `web_app/`

1. `web_app/run.py`
   - `create_app()` 호출 → `app` 생성, `app.run(host=0.0.0.0, port=5000, debug=True)`.
2. `web_app/app/__init__.py` → `create_app()`
   - `Flask(...)` 생성, `frontend/`를 `/static`으로 서빙.
   - `app.config.from_object(Config)` — `web_app/app/config.py`의 `Config`. `get_required_env()`로 DB URL 등 필수 환경변수 로드, `BRIDGE_BASE_URL`(기본 `http://127.0.0.1:8001`), `BRIDGE_TIMEOUT_SECONDS` 설정.
   - `db.init_app(app)` — `web_app/app/extensions.py`의 `db = SQLAlchemy()`.
   - Blueprint 등록: `pages / health / work_orders / bridge / executions / logs / robots / dashboard / sensor_data / installations`.

### 1-2. ROS2 Bridge — `src/ros2_bridge/ros2_bridge/bridge_node.py`

1. `main(args)`
   - `rclpy.init()` → `Ros2BridgeNode()` 생성 → `create_http_app(node)` → `run_http_server()`가 별도 스레드에서 Flask(`:8001`) 기동 → `rclpy.spin(node)`.
2. `Ros2BridgeNode.__init__()`
   - `job_queue = Queue()` (Operation 단위 작업 큐).
   - `action_client = ActionClient(ExecuteOperation, "execute_operation")`.
   - 상태 필드: `_goal_in_progress`, `_status`, `_last_job`, `_stopped_work_execution_ids`, `_accepted_work_execution_ids`.
   - `create_subscription(SystemEvent, "/system_event", system_event_callback, 10)`.
   - `system_event_thread` 시작 → `process_system_events()` 루프.
   - `create_timer(0.1, process_job_queue)` — 100 ms 주기로 큐를 소비.
   - `create_client(StopOperation, "stop_operation")`, `create_client(RecoverRobot, "recover_robot")`.
3. `create_http_app(node)` — 내부에 HTTP 라우트 정의 후 `http_app` 반환:
   - `GET /health` → `health_check()`
   - `GET /status` → `get_status()` → `node.get_bridge_status()`
   - `POST /works/<work_execution_id>/stop` → `stop_work()` → `node.request_work_stop()`
   - `POST /robots/<robot_id>/recover` → `recover_robot()` → `node.request_robot_recovery()`
   - `POST /jobs` → `create_job()` → `validate_work_command()` → `node.enqueue_work()`

### 1-3. Controller — `src/solar_panel_robot/solar_panel_robot/controller_node.py`

1. `main(args)`
   - `rclpy.init()`, `DR_init.__dsr__id / __dsr__model` 설정.
   - `SolarPanelControllerNode()` 생성.
   - 별도 `dsr_node = rclpy.create_node("solar_robot_dsr_client")` 생성 후 `DR_init.__dsr__node`에 지정 (DSR_ROBOT2 서비스 호출 전용, Action/Timer 노드와 분리).
   - `controller_node.setup_components()` 호출.
   - `MultiThreadedExecutor(num_threads=2)`에 노드 추가 후 spin.
2. `SolarPanelControllerNode.__init__()`
   - `status_publisher = create_publisher(String, "status")` (namespace `/{robot_id}` → `/1/status`).
   - `declare_parameter("robot_id", 1)` → `backend_robot_id`.
   - `system_event_publisher = create_publisher(SystemEvent, "/system_event")`.
   - `status_timer = create_timer(1.0, publish_current_status)`.
   - `action_server = ActionServer(ExecuteOperation, "execute_operation", execute_callback, goal_callback, cancel_callback)`.
   - `create_service(StopOperation, "/stop_operation", stop_operation_callback)`.
   - `create_service(RecoverRobot, "/recover_robot", recover_robot_callback)`.
   - `set_status("STARTING")`.
3. `setup_components()`
   - `set_status("INITIALIZING")`.
   - `RobotController(self)` 생성 → `.initialize()`:
     - `_call_with_retry("Manual Mode", ...)` → `SetRobotMode(MANUAL)`
     - `_call_with_retry("Tool ToolWeight", ...)` → `SetCurrentTool`
     - `_call_with_retry("TCP GripperDA_v1", ...)` → `SetCurrentTcp`
     - `_call_with_retry("Auto Mode", ...)` → `SetRobotMode(AUTO)`
     - 각 단계 3회 재시도, 실패 시 `publish_system_event(CRITICAL, "INITIALIZE_FAILED")` 후 `RuntimeError`.
   - `publish_system_event(INFO, "ROBOT_INITIALIZED")`.
   - `SolarMotion(self)` 생성 → 내부에서 `RobotMotion()`(+`ForceController`) 로드.
   - `solar.motion.release()` (초기 그리퍼 open), `solar.motion.move_home()` (초기 Home). 실패해도 WARNING 이벤트 후 계속.
   - `set_status("READY")`, `publish_system_event(INFO, "ROBOT_READY")`.

### 1-4. Mock Action Server — `src/solar_panel_robot/solar_panel_robot/action_server.py`

`main()` → `ExecuteOperationServer()` → `MultiThreadedExecutor` spin.
`__init__()`에서 `ActionServer("execute_operation")` + `create_service(StopOperation, "stop_operation")` + `create_service(RecoverRobot, "recover_robot")`. 실제 Controller와 같은 이름이므로 **둘 중 하나만** 실행한다.

## 2. 정상 작업 실행 시퀀스 (Work Order 1건)

현장 관리자가 Dashboard에서 READY 상태 Work Order를 "실행"하면 아래 순서로 흐른다.

### 2-1. Backend: 실행 요청 수신

**`web_app/app/routes/work_orders.py` → `execute_work_order(work_order_id)`** (`POST /api/v1/work-orders/<id>/execute`)

1. 요청 body에서 `robot_id`(양의 정수) 검증.
2. `get_work_order_by_id()` — Work Order 존재 + `status == "READY"` 확인.
3. `get_robot_by_id()` — Robot 존재 + `status == "IDLE"` 확인.
4. `get_operations_for_installation(work_order.installation_id)` — 설치 대상의 Operation 목록(순서대로) 조회.
5. `get_active_work_execution()` — 이미 실행 중인 Execution 없는지 확인.
6. `create_execution_records_for_operations(work_order_id, operations, robot_id)`
   → `web_app/app/services/execution_service.py`
   - `generate_execution_number()`로 실행 번호 생성.
   - `WorkExecution` 1건 + Operation 수만큼 `OperationExecution`(`sequence` 부여, `status="PENDING"`) 생성.
7. `build_work_command(...)` → `web_app/app/services/bridge_service.py`
   - `OperationExecution`을 `sequence` 순으로 정렬.
   - 각 항목을 `{operation_execution_id, operation_id, operation_code, sequence, parameters, components}`로 변환.
   - `{work_order_id, work_execution_id, robot_id, operations[]}` dict 반환.
8. `submit_bridge_work(command)` → `POST {BRIDGE_BASE_URL}/jobs` (HTTP).
   - 연결 실패 → `BridgeConnectionError` → `mark_work_submission_failed()` 후 503.
   - Bridge가 202/`success` 아니면 → `BridgeResponseError` → 502.
9. `mark_work_execution_running(work_order, work_execution, robot)`
   - Work Order `RUNNING`, WorkExecution `RUNNING`, Robot `RUNNING`.
10. HTTP 202 반환(생성된 execution 정보 + bridge 응답).

### 2-2. Bridge: 작업 큐 적재

**`bridge_node.py` → `create_job()`** (`POST /jobs`)

1. `validate_work_command(request_data)` — 최상위 필드/`operations[]` 각 항목 검증(`validate_operation_item()`).
2. `operations`를 `sequence` 순으로 정렬, `bridge_work_id = uuid4()` 부여.
3. `node.enqueue_work(work)` 호출, HTTP 202 반환.

**`Ros2BridgeNode.enqueue_work(work)`**

- `work_execution_id`가 `_accepted_work_execution_ids`에 있으면 중복 → `False` 반환(재적재 안 함).
- 없으면 등록 후, **Operation마다 job 1건**을 만들어 `job_queue.put(job)`. → 한 Work의 모든 Operation이 큐에 한 번에 쌓인다.

### 2-3. Bridge: Operation 순차 디스패치

**`Ros2BridgeNode.process_job_queue()`** — 100 ms 타이머

1. `_goal_in_progress`면 즉시 반환(한 번에 Operation 1건).
2. `action_client.server_is_ready()` 확인 → `update_action_server_status()`로 연결 상태 변화 시 `enqueue_bridge_log()`. 미준비면 `_status="ACTION_SERVER_UNAVAILABLE"` 후 반환.
3. `job_queue.get_nowait()`로 1건 꺼냄.
4. 해당 `work_execution_id`가 `_stopped_work_execution_ids`에 있으면 **스킵**(정지된 작업의 잔여 Operation 버림).
5. `_goal_in_progress=True`, `_status="SENDING_GOAL"`, `_last_job=job`.
6. `ExecuteOperation.Goal()` 채움: `work_order_id / work_execution_id / operation_id / operation_code / operation_execution_id / robot_id`, `parameters`는 `convert_parameters()`(dict → `Parameter[]`, 비문자열은 `json.dumps`), `components`는 `json.dumps`.
7. `action_client.send_goal_async(goal, feedback_callback=self.feedback_callback)`
   → `.add_done_callback(self.goal_response_callback)`.

**`goal_response_callback(future)`**

- 전송 실패 → `stop_current_work("GOAL_SEND_FAILED")` + `notify_backend_dispatch_failure()`.
- `goal_handle.accepted`가 False → `stop_current_work("GOAL_REJECTED")` + `notify_backend_dispatch_failure()`.
- 수락 시 `_status="EXECUTING"`, `goal_handle.get_result_async().add_done_callback(self.result_callback)`.

### 2-4. Controller: Goal 수락 판정

**`controller_node.py → goal_callback(goal_request)`**

순서대로 REJECT 조건 검사: `solar is None`(준비 안 됨) → `_robot_stopped`(복구 필요) → ID 중 0 이하 → `parse_components()` 실패 → `current_status == "ERROR"` → `robot_id != backend_robot_id` → `resolve_operation_code()` 실패(`SUPPORTED_OPERATION_CODES` 아님) → `operation_running`(다른 Operation 진행 중).
모두 통과하면 `operation_running=True`, `GoalResponse.ACCEPT`.

### 2-5. Controller: Operation 실행

**`controller_node.py → execute_callback(goal_handle)`**

1. `_active_goal_handle=goal_handle`, `_stop_requested=False`.
2. `request`에서 ID 파싱, `resolve_operation_code()`, `parse_parameters()`(`Parameter[]` → dict, `json.loads` 시도), `parse_components()`(JSON 문자열 → list).
3. `operation_context` dict 구성.
4. `set_status("RUNNING")`.
5. `publish_system_event(INFO, "OPERATION_STARTED", phase="OPERATION", status="STARTED")` → `/system_event` 발행.
6. `publish_feedback(goal_handle, op_exec_id, STATUS_RUNNING, ...)` → `ExecuteOperation.Feedback` 발행.
7. 취소/정지 요청 확인 → 있으면 `complete_cancelled_operation()`.
8. **`execute_operation(operation_code, parameters, components, operation_context)`** — 실제 동작 분기(2-6).
9. 다시 취소 확인.
10. `publish_feedback(..., STATUS_COMPLETED, ...)`, `goal_handle.succeed()`, `result.success=True`.
11. `publish_system_event(INFO, "OPERATION_COMPLETED", status="COMPLETED")`, `set_status("READY")`.
12. 예외 발생 시: 취소 상태면 `complete_cancelled_operation()`, 아니면 `solar.force.all_off()` → `publish_feedback(STATUS_FAILED)` → `goal_handle.abort()` → `result.error_code="OPERATION_FAILED"` → `publish_system_event(ERROR, "OPERATION_FAILED")` → `set_status("ERROR")`.
13. `finally`: `_active_goal_handle` 정리, `operation_running=False`.

**`execute_operation(...)`** — `operation_code`별 분기(→ `SolarMotion` 메서드):

| operation_code | 호출 | 비고 |
|---|---|---|
| `POST_OPERATION_CODES`(postA/B/C …), `POST_INSTALL` | `solar.install_post_cycle()` | 현재 주 경로 |
| `POST_PICK` / `POST_PLACE` | `solar.pick_post()` / `solar.place_post()` | 단독 테스트 |
| `POST_PIN_PICK` / `POST_PIN_PLACE` | `solar.pick_post_pin()` / `solar.place_post_pin()` | ⚠️ `SolarMotion`에 해당 메서드 미구현 — 이 코드로는 호출 불가 |
| `PANEL_PICK` | `solar.pick_panel()` | 단독 테스트 |
| `SOLAR_FULL` | `solar.run()` | 전체 시연 |

### 2-6. 로봇 동작 레이어 — `src/solar_panel_robot/solar_panel_robot/`

**`solar_motion.py → SolarMotion.install_post_cycle(parameters, components, operation_context)`**

1. `_publish_cycle_event(phase="POST_CYCLE", status="STARTED")`.
2. `_load_travel_settings(parameters)` — 이동 speed/acc(누락 시 안전 기본값).
3. `pick_post(...)`:
   - `_load_pick_settings()`, `_post_pickup_input(components)` → `pickup_position`.
   - `movel` Safe Pick(위 +Z `pick_distance`) → `movel` 정확 Pick → `motion.grasp()` → Safe Pick 복귀.
4. `place_post(...)` → `post_retreat` 반환:
   - `_load_post_place_settings()`, `_post_assembly_input()` → `assembly_position`.
   - `movel` Safe Place → 정확 Place 위치 → `_search_post_alignment()`(접촉점 주변 force probe로 정렬점 탐색) → `motion.place()` Force 삽입.
5. `motion.stop_motion()` + `force.all_off()`.
6. `motion.release()` (그리퍼 open).
7. `post_retreat > 0`이면 동일 Safe Place(BASE +Z)로 `movel` 복귀.
8. `motion.move_home()`.
9. `_publish_cycle_event(status="COMPLETED")`, `return True`. 예외 시 `force.all_off()` 후 `PostCycleError`.

**`coordinate_manager.py → CoordinateManager`** — 사용자 좌표계

| 함수 | 기능 |
|---|---|
| `_validate_pose(pose, label)` | 6요소 pose 검증 |

| `get_id()` | 생성된 coord_id 반환 |
| `get_current_pose()` | 해당 사용자 좌표계 기준 현재 pose |

> `SolarMotion`의 `pick_pin / place_pin / pick_frame / place_frame / pick_panel / pick_snapfit / place_snapfit / place_post / install_post_cycle / run`은

### 2-7. Bridge → Backend 콜백

**`feedback_callback(feedback_message)`** (Operation 실행 중 반복)

- `_last_job`과 `operation_execution_id` 일치 확인.
- `notify_backend_action_feedback(job, feedback)` → `POST {BACKEND_BASE_URL}/api/v1/executions/action-feedback` `{work_execution_id, operation_execution_id, status(int), message}`.
- `_status`를 `PENDING/RUNNING/COMPLETED/FAILED/CANCELLED`로 갱신.

**`result_callback(future)`** (Operation 종료 시 1회)

- 수신 실패 → `stop_current_work("RESULT_FAILED")` + `notify_backend_dispatch_failure()`.
- `result.success` → `COMPLETED` / `error_code=="CANCELLED"` → `CANCELLED` / 그 외 → `FAILED`.
- 실패 시 `_stopped_work_execution_ids.add(work_execution_id)` (잔여 Operation 중단).
- `notify_backend_action_result(job, result)` → `POST /api/v1/executions/action-result` `{work_execution_id, operation_execution_id, success, error_code, message}`.
- 성공 시 `_goal_in_progress=False` → 다음 타이머에서 `process_job_queue()`가 다음 Operation 디스패치.

### 2-8. Backend: 콜백 처리 및 진행 판정

**`web_app/app/routes/executions.py → receive_action_feedback()`** (`POST /api/v1/executions/action-feedback`)

- `work_execution_id / operation_execution_id`(양의 정수), `status`(0~4) 검증.
- `get_work_execution_by_id()`, `get_operation_execution_by_id()`, 소속 일치 확인.
- `status == RUNNING`이면 `mark_operation_running(operation_execution)` (PENDING→RUNNING), 첫 전이면 `create_system_log(EVENT, "OPERATION_STARTED")`.
- 응답에 `final_state_pending_result`(COMPLETED/FAILED/CANCELLED 여부) 포함.

**`receive_action_result()`** (`POST /api/v1/executions/action-result`)

- ID/소속/`WorkOrder`/`Robot` 존재 검증, 중복 콜백(이미 COMPLETED/FAILED/CANCELLED) 무시.
- 상태 전이 허용 검사: 성공 결과는 `RUNNING`만, 실패 결과는 `PENDING/RUNNING`.
- **취소**(`success=False && error_code=="CANCELLED"`): `mark_execution_cancelled()` + `create_system_log(EVENT, "OPERATION_CANCELLED")`.
- **실패**: `mark_execution_failed()` + `create_system_log(ERROR, ...)`.
- **성공**: `mark_operation_completed()` + `create_system_log(EVENT, "OPERATION_COMPLETED")`.
  - `get_next_pending_operation_execution()`:
    - 없으면 → `mark_execution_completed()` (WorkOrder/WorkExecution/Robot 종료), `workflow_status="COMPLETED"`.
    - 있으면 → `workflow_status="RUNNING"`, `has_next_operation=True`.
      (다음 Operation은 Bridge `job_queue`에 이미 있으므로 재전송 없음 — Backend는 상태만 갱신.)

### 2-9. 시퀀스 요약

```
Dashboard
  └─(POST /work-orders/<id>/execute)─▶ execute_work_order()
        create_execution_records_for_operations()  [WorkExecution + OperationExecution*]
        build_work_command()
        submit_bridge_work() ─(POST /jobs)─▶ create_job() ─▶ enqueue_work() [job_queue에 Operation 전건 적재]
        mark_work_execution_running()

Bridge 타이머(100ms): process_job_queue()  ── Operation 1건씩 ──┐
   send_goal_async(ExecuteOperation.Goal) ──▶ Controller.goal_callback() ─▶ ACCEPT
   goal_response_callback() ─▶ get_result_async()
                                                                            │
   Controller.execute_callback()                                            │
     publish_system_event(OPERATION_STARTED) ──/system_event──▶ Bridge.system_event_callback()
     publish_feedback(RUNNING) ──Action Feedback──▶ Bridge.feedback_callback()
                                            └─(POST /executions/action-feedback)─▶ receive_action_feedback() ─▶ mark_operation_running()
     execute_operation() ─▶ SolarMotion.install_post_cycle() ─▶ RobotMotion / ForceController
     publish_feedback(COMPLETED)
     goal_handle.succeed() ──Action Result──▶ Bridge.result_callback()
                                            └─(POST /executions/action-result)─▶ receive_action_result()
                                                  mark_operation_completed()
                                                  get_next_pending_operation_execution()
                                                    ├─ 있음 ─▶ RUNNING (다음 루프에서 process_job_queue가 다음 Operation)
                                                    └─ 없음 ─▶ mark_execution_completed() ─▶ COMPLETED
```

## 3. 강제 정지 · 로봇 복구 시퀀스

### 3-1. 강제 정지

**`web_app/app/routes/work_orders.py → stop_work_order(work_order_id)`** (`POST /api/v1/work-orders/<id>/stop`)

1. Work Order `status == "RUNNING"`, `get_active_work_execution()` 확인.
2. `stop_bridge_work(work_execution_id)` → `POST {BRIDGE_BASE_URL}/works/<id>/stop`.
3. `get_robot_by_id()`, `mark_robot_stop_requested(robot)`.
4. `create_system_log(EVENT, "WORK_STOP_REQUESTED", severity=WARNING, detail={stop_type: FORCED})`.
5. HTTP 202, `terminal_state_pending=True`(최종 상태는 이후 `action-result` 콜백으로 확정).

**`bridge_node.py → stop_work()` → `Ros2BridgeNode.request_work_stop(work_execution_id)`**

1. `_last_job`이 해당 `work_execution_id`이고 `_goal_in_progress`인지 확인 → 아니면 `WORK_NOT_ACTIVE`.
2. `_stopped_work_execution_ids.add(...)`, `_status="STOP_REQUESTED"` — **이후 큐의 잔여 Operation은 `process_job_queue()`에서 스킵**.
3. `stop_operation_client.service_is_ready()` 확인 → 아니면 `STOP_SERVICE_UNAVAILABLE`.
4. `StopOperation.Request(work_execution_id, operation_execution_id, robot_id)` → `call_async`, `CONTROLLER_SERVICE_TIMEOUT` 대기.
5. `response.accepted` → `_status="STOP_ACCEPTED"` 및 accept 응답.

**Controller `stop_operation_callback(request, response)`**

- `_active_goal_handle` 활성 + 요청 ID 일치 확인(`OPERATION_NOT_ACTIVE` / `EXECUTION_MISMATCH`).
- `_stop_requested=True` → `solar.motion.stop_motion()` + `solar.force.all_off()`.
- 실패 시 `set_status("ERROR")`, `ROBOT_STOP_FAILED`.
- 성공 시 `_robot_stopped=True`, `set_status("STOPPED")`, `response.accepted=True`.
- 실행 중이던 `execute_callback`은 다음 `_stop_requested` 확인 지점에서 `complete_cancelled_operation()` → `goal_handle.canceled()` → `result.error_code="CANCELLED"` → Bridge `result_callback` → Backend `receive_action_result`(취소 경로) → `mark_execution_cancelled()`.

> Mock(`action_server.py`)의 `stop_operation_callback`은 실제 모션 대신 `_stop_requested/_robot_stopped` 플래그만 세팅하고, `execute_callback` 루프가 다음 진행 단계에서 `STATUS_CANCELLED` feedback + `goal_handle.canceled()`.

### 3-2. 로봇 복구

**`web_app/app/routes/robots.py → recover_robot(robot_id)`** (`POST /api/v1/robots/<id>/recover`)

1. Robot `status == "ERROR"` 확인(`ROBOT_RECOVERY_NOT_REQUIRED`).
2. `create_system_log(ROBOT, "ROBOT_RECOVERY_REQUESTED")`.
3. `recover_bridge_robot(robot_id)` → `POST {BRIDGE_BASE_URL}/robots/<id>/recover`.
4. `mark_robot_recovered(robot)` (ERROR→IDLE), `create_system_log(ROBOT, "ROBOT_RECOVERY_COMPLETED")`.

**`bridge_node.py → recover_robot()` → `request_robot_recovery(robot_id)`**
→ `RecoverRobot.Request(robot_id)` → Controller `/recover_robot`.

**Controller `recover_robot_callback(request, response)`**

- `robot_id == backend_robot_id` 확인(`ROBOT_ID_MISMATCH`).
- `_active_goal_handle` 비활성 확인(`OPERATION_ACTIVE`).
- `solar.motion.restore_motion()` (Force 해제 + Home 복귀).
- 성공 시 `_active_goal_handle=None`, `_stop_requested=False`, `_robot_stopped=False`, `set_status("READY")`, `response.recovered=True`.

## 4. 이벤트 · 로그 시퀀스 (`/system_event` → SystemLog)

1. Controller `publish_system_event(severity, code, message, work_execution_id=, operation_execution_id=, operation_code=, phase=, status=, detail=)`
   → `SystemEvent` 메시지를 `/system_event`에 발행.
   (발행 시점: `ROBOT_INITIALIZED`, `ROBOT_READY`, `INITIALIZE_RETRY/FAILED`, `OPERATION_STARTED/COMPLETED/FAILED/CANCELLED`, 각 Cycle 단계 `_publish_cycle_event`)
2. Bridge `system_event_callback(event)`
   - `severity` 유효성, `robot_id > 0`, `code`/`message` 비어있지 않은지 검사.
   - `system_event_queue.put({...})`.
3. Bridge `process_system_events()` (전용 스레드 루프)
   - `notify_backend_system_event(event)` → `POST {BACKEND_BASE_URL}/api/v1/logs`.
   - `detail` JSON 파싱, `operation_code/phase/status`를 `detail`에 병합.
4. Bridge 자체 로그: `enqueue_bridge_log(severity, code, message)` → 같은 큐 → `log_type="SYSTEM"` (예: `BRIDGE_ACTION_SERVER_CONNECTED/DISCONNECTED`).
5. Backend **`web_app/app/routes/logs.py → add_log()`** (`POST /api/v1/logs`)
   - `create_system_log(...)` → `web_app/app/services/log_service.py` → `SystemLog` 레코드 저장(HTTP 201).
6. 조회: `list_logs()` (`GET /api/v1/logs`, `parse_optional_id()`로 필터), `get_system_logs()`.

> Backend 내부 상태 전이(`receive_action_feedback/result`, `execute/stop_work_order`, `recover_robot`)도 `create_system_log()`를 직접 호출해 `EVENT/ERROR/ROBOT` 로그를 남긴다.

## 6. 주의 (CLAUDE.md 기준)

- `stop_operation` / `recover_robot` 서비스 서버는 **Mock(`action_server.py`)과 실제 `controller_node.py` 양쪽에 구현**되어 있으나, 실제 로봇에서의 end-to-end 검증은 아직 Mock 기준이다.
- 별도 `ros_bridge_node.py`는 현재 저장소에 없다. HTTP↔ROS2 변환은 `src/ros2_bridge`가 전담한다.
- `controller_node.execute_operation()`의 `POST_PIN_PICK/POST_PIN_PLACE` 분기는 `SolarMotion`에 대응 메서드가 없어 호출 시 `AttributeError`가 난다(주 경로인 `install_post_cycle`에는 영향 없음).
- Operation 순서는 **Backend가 아니라 Bridge `job_queue`가 보장**한다. Backend는 `receive_action_result`에서 다음 Operation을 "판정"만 하고 재전송하지 않는다.
