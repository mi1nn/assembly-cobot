# 소스코드 역할 정리

> 미팅 설명용 자료. `develop/test` 브랜치 기준.

## 전체 그림

```
Dashboard(HTML/JS) → Flask Backend(web_app) → PostgreSQL
                            │ HTTP
                            ▼
                    ROS2 Bridge (src/ros2_bridge)
                            │ ROS2 Action / Topic
                            ▼
                  Controller (src/solar_panel_robot)
                            │
                            ▼
                    Doosan M0609 + Gripper + F/T Sensor
```

인터페이스 정의(`src/solar_panel_interface`)는 Bridge ↔ Controller 사이에서만 쓰입니다.

---

## 1. `src/solar_panel_interface` — 통신 인터페이스 정의 (ament_cmake)

Bridge와 Controller가 주고받는 메시지/액션의 "계약"만 정의하는 패키지. 로직 없음.

| 파일 | 역할 |
|---|---|
| `action/ExecuteOperation.action` | Bridge → Controller로 Operation 하나를 실행시키는 ROS2 Action. Goal(work_order_id, work_execution_id, operation_id, operation_code, operation_execution_id, robot_id, parameters, components) / Result(성공 여부, error_code) / Feedback(operation_execution_id, status, message) |
| `msg/Parameter.msg` | Operation 실행에 필요한 key-value 파라미터 하나 (DB의 JSON 파라미터를 문자열로 실어 나름) |
| `msg/SystemEvent.msg` | Controller → Bridge로 보내는 이벤트/오류 알림 메시지(robot_id, severity, code, message, work_execution_id, operation_execution_id 등). Controller가 `/system_event`로 publish하고 Bridge가 subscribe해서 Backend `/api/v1/logs`로 전달 — 양쪽 다 연결된 상태 |

---

## 2. `src/solar_panel_robot` — 로봇 제어 노드 (ament_python)

실제 로봇을 움직이는 계층. 두산 SDK(`DSR_ROBOT2`)를 직접 호출합니다.

| 파일 | 역할 |
|---|---|
| `controller_node.py` | **ExecuteOperation Action Server (entry point: `controller`).** Bridge로부터 Goal을 받아 `resolve_operation_code()`로 DB operation.code(`postA`~`postF` 등)를 검증하고, robot_id 일치·Controller 상태(ERROR 아님)·동시 실행 중복 여부를 확인해 Goal을 승인/거부. 승인 후 `SolarMotion`에 실제 동작을 위임하고 Feedback(IF-15)/Result 응답. `/system_event`로 초기화·Operation 진행·오류·복구 이벤트를 publish. Cancel은 아직 미지원(항상 REJECT) |
| `action_server.py` | 실제 로봇 없이 통신 흐름만 검증하는 **Mock Action Server (entry point: `action_server`)**. Goal→Feedback→Result 진행률 시뮬레이션, 환경변수로 강제 실패 테스트, 그리고 `stop_operation_callback`/`recover_robot_callback`로 Backend의 강제정지·복구 흐름도 모킹 |
| `robot_controller.py` | 로봇 초기화 전용. Manual/Auto 모드 전환, Tool/TCP(그리퍼 장착 정보) 설정, SDK 호출 재시도(`_call_with_retry`) |
| `robot_motion.py` | **저수준 모션 라이브러리.** movej/movel 등 SDK 함수를 감싸서 pick/place, 원점 복귀, 힘 감지 이동 등 범용 로봇 동작 제공. 그리퍼 on/off도 여기 있음 |
| `solar_motion.py` | **공정별 상위 시나리오.** "프레임 Pick → 배치 → 설치", "핀 Pick → 삽입(1차/최종)" 등 태양광 조립 공정 순서를 `robot_motion.py`/`force_control.py`를 조합해 구현. `controller_node.py`가 실제로 호출하는 대상. **아직 `coordinate_manager.py`는 참조하지 않음** — Frame 좌표계 측정 연동 전 상태 |
| `force_control.py` | **F/T 센서 기반 힘 제어.** Compliance(순응 제어) on/off, 목표 힘 설정, 힘 조건 체크 — CLAUDE.md의 "잠금핀 삽입" 로직 담당 |
| `coordinate_manager.py` | **(신규) Frame 좌표계 생성 유틸.** DB에서 받은 UCS(P1/P2/P3, 각 6DOF pose)로 Doosan `set_user_cart_coord()`를 호출해 사용자 좌표계를 생성하고 좌표계 ID를 캐싱(동일 P1/P2/P3면 재생성 안 함). `get_current_pose()`로 해당 좌표계 기준 현재 위치 조회 가능. **`CoordinateManager`는 아직 `coord_manager_test.py`에서만 사용되고, `solar_motion.py`/`controller_node.py` 실제 공정 흐름에는 연결되지 않은 상태** — CLAUDE.md 핵심 기술 ②③(실측 기반 좌표계 생성/후속 동작)의 통합 지점이 여기 |
| `coord_manager_test.py` | `CoordinateManager` 단독 동작 확인용 수동 실행 스크립트(`main()`) |
| `config_loader.py` | `config/poses.yaml`(위치/자세, 속도, 그리퍼 포트값)을 로딩해주는 유틸 |
| `ros_bridge_node.py` | Controller를 직접 호출하는 별도 Action Client. **`src/ros2_bridge`와 별개의 코드** — `setup.py`의 `console_scripts`에도 등록되어 있지 않아 실행조차 되지 않는 미사용 코드 (정리 필요 항목) |
| `config/poses.yaml`, `launch/solar_robot.launch.py` | 설정값 파일 / 노드 실행용 launch 파일 |

## 3. `src/ros2_bridge` — Backend ↔ ROS2 브릿지 (ament_python)

| 파일 | 역할 |
|---|---|
| `bridge_node.py` | 한 프로세스에 두 가지가 같이 떠 있음: ① Flask HTTP 서버(포트 8001) — Backend의 요청을 받는 `/health`, `/status`, `/jobs`(Operation 제출), `/works/<id>/stop`(강제 정지), `/robots/<id>/recover`(복구) 엔드포인트 제공. ② rclpy ActionClient — 받은 Operation들을 큐에 쌓고 순서대로 Controller에 Action Goal 전송, Feedback/Result를 받으면 Backend의 `/api/v1/executions/action-feedback`, `/action-result`로 콜백. 또한 Controller가 publish하는 `/system_event`를 subscribe해서 Backend `/api/v1/logs`로 전달. 한 Operation이 실패하면 같은 작업의 나머지 대기 Operation은 자동으로 건너뜀 |

## 4. `web_app` — Flask Backend (Work Order / Recipe 관리)

| 위치 | 역할 |
|---|---|
| `app/models/` | DB 테이블 매핑: `WorkOrder`, `Operation`, `WorkExecution`, `OperationExecution`, `Robot`, `Installation`, `SystemLog`, `SensorData` (schema.sql 기준 9개 테이블 중 `sensor`는 아직 모델 매핑 없음) |
| `app/routes/work_orders.py` | Work Order CRUD, `/execute`(Bridge에 전체 Operation 제출), `/progress`(진행률 조회), `/stop`(RUNNING 중인 Work Order 강제 정지 — Bridge `/works/<id>/stop` 호출 후 실행 상태를 CANCELLED로 마킹) |
| `app/routes/executions.py` | Bridge가 호출하는 콜백 2종(`/action-feedback`, `/action-result`) — 실행 상태를 DB에 반영, 다음 Operation으로 진행 처리 |
| `app/routes/robots.py` | `GET /`(로봇 목록 + 현재 실행 중인 Work 정보 조인), `POST /<id>/recover`(ERROR 상태 로봇을 Bridge `/robots/<id>/recover` 호출로 복구, 시스템 로그 기록) |
| `app/routes/dashboard.py` | 대시보드용 집계 데이터(`/api/v1/dashboard`) 단일 엔드포인트 |
| `app/routes/bridge.py` | Bridge 헬스체크 프록시 |
| `app/routes/logs.py` | 시스템 로그 조회/기록 API — ROS `SystemEvent`가 Bridge를 거쳐 여기로 들어옴(연결됨) |
| `app/routes/sensor_data.py` | Operation Execution 기준 센서 데이터 조회(`GET /api/v1/sensor-data`) |
| `app/routes/health.py`, `pages.py` | Backend 자체 헬스체크, 정적 대시보드 페이지 서빙 |
| `app/services/bridge_service.py` | Bridge HTTP 클라이언트: `/jobs` 제출용 Work Command 조립(`build_work_command`), `submit_bridge_job/work`, `stop_bridge_work`, `recover_bridge_robot`, 연결/응답 오류 예외(`BridgeConnectionError`, `BridgeResponseError`) |
| `app/services/dashboard_service.py` | 로봇별 활성 실행 요약, 성공률 등 대시보드 집계 쿼리 |
| `app/services/robot_service.py` | 로봇 목록 조회, 로봇별 활성 Work Execution 조회 |
| `app/services/execution_service.py` | Execution/Operation Execution 상태 전이 로직 전반(진행/완료/실패/취소/강제정지/로봇 복구 포함) |
| `app/services/work_order_service.py`, `operation_service.py`, `log_service.py` | 각각 Work Order CRUD, Operation 조회, 시스템 로그 생성/조회 |
| `database/schema.sql`, `seed.sql` | PostgreSQL 스키마(9개 테이블: installation, operation, robot, sensor, work_order, work_execution, operation_execution, log, sensor_data)와 데모용 초기 데이터 |
| `frontend/` | 정적 HTML/CSS/JS 대시보드 (Work Order 생성·조회·실행·강제정지, 로봇 상태·복구, 시스템 로그 조회 UI) |

## 한 줄 요약 (발표용)

- **`solar_panel_interface`**: 통신 규격만 정의 (Action + SystemEvent 모두 실제로 쓰이는 중).
- **`solar_panel_robot`**: 로봇을 실제로 움직이는 계층 (모션 + 힘제어 + 공정 시나리오 + Action Server). `coordinate_manager.py`는 만들어졌지만 아직 공정 흐름에 통합 전.
- **`ros2_bridge`**: HTTP(Backend) ↔ ROS2(로봇) 사이를 번역하는 중계 노드. Operation 제출/강제정지/복구/시스템 이벤트까지 양방향 연결됨.
- **`web_app`**: Work Order/Recipe 관리 + 로봇 상태·강제정지·복구 + DB + 사용자용 대시보드.
